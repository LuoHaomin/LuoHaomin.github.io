5.1 并行的层次与分类

5.1.1 Flynn分类法 (1966)

类型 全称 说明 应用
SISD Single Instruction Single Data 单处理器 传统CPU
SIMD Single Instruction Multiple Data 同一指令操作不同数据 向量机、GPU
MISD Multiple Instruction Single Data 多指令单数据 无商用实现
MIMD Multiple Instruction Multiple Data 多指令多数据 多核处理器

5.1.2 并行的层次（从粗到细）

层次 说明 典型应用
请求级并行 多任务分配到多台计算机 分布式计算、集群
进程级并行 进程调度到不同处理器 多进程编程
线程级并行 多线程共享地址空间 多线程应用
数据级并行 单线程并行处理多个数据 SIMD、Vector
指令级并行 (ILP) 多条指令并行执行 流水线、乱序执行

⭐ 重点：ILP针对单一指令流，多个执行部件并行执行不同指令

5.1.3 基本流水线回顾

流水线提高的是指令吞吐率，而非单条指令的执行速度

相关类型：

  • 结构相关：需要更多硬件资源
  • 数据相关：需要定向、编译器调度
  • 控制相关：尽早检测条件、计算目标地址、延迟转移、预测

关键结论：增加流水线级数会增加相关产生的可能性

5.3 软件方法：基本块内ILP

5.3.1 基本块 (Basic Block)

定义：直线型代码，无分支，单入口单出口

特点：

  • 程序由分支语句连接基本块构成
  • 基本块内并行度有限（通常2-3条指令）
  • 循环级并行：不同迭代之间可能存在并行性

5.3.2 数据相关类型

1. 真数据相关 (True Dependence / RAW)

定义：指令j使用指令i产生的结果

特点：必须等待，无法消除

2. 名字相关 (Name Dependence)

反相关 (Antidependence / WAR)：

  • 指令j写的寄存器，指令i读
  • 可通过寄存器重命名消除

输出相关 (Output Dependence / WAW)：

  • 指令i和j写同一寄存器
  • 可通过寄存器重命名消除

3. 控制相关 (Control Dependence)

定义：受分支指令控制的指令

处理原则：

  • 受分支控制的指令不能移到分支之前
  • 不受分支控制的指令不能移到分支之后

5.3.3 循环展开 (Loop Unrolling)

目的：增大基本块，暴露更多指令级并行性

步骤：

  1. 将循环体复制N次
  2. 调整循环步长（step × N）
  3. 调整寄存器使用（消除重复使用同名寄存器）
  4. 消除多余的分支指令

关键操作：

  • 寄存器重命名：消除名字相关（WAR/WAW）
  • 指令调度：重新排列指令减少stall

  • 通过寄存器重命名（F0→F6→F10→F14）消除WAW相关

5.3.4 循环间相关 (Loop-Carried Dependence)

定义：存在于不同循环迭代之间的相关

示例：

  • S2使用S1在同一循环计算的A[i+1]
  • 存在”loop-carried dependence”→循环间相关，不能完全并行执行

处理方法：

  1. 依赖距离分析：如果依赖距离>1，可通过循环展开并行化
  2. 循环变换：重新组织循环顺序
  3. 递推关系展开：将递推关系展开为并行计算

5.4 硬件方法(一)：记分牌 (Scoreboard)

5.4.1 CDC 6600记分牌 (1963)

目标：允许乱序执行（Out-of-Order Execution），但顺序写回

5.4.2 记分牌的三种结构

结构 内容 字段数
指令状态表 每条指令的Issue/Read/Execute/Write状态 4阶段
功能单元状态表 Busy/Op/Fi/Fj/Fk/Qj/Qk/Rj/Rk 9个字段
寄存器结果表 每个寄存器对应的正在写入的功能单元 F0-F30

5.4.3 记分牌控制的四阶段

阶段 功能 Stall条件
Issue 分配RS，检查WAW 功能单元忙 或 目的寄存器有其他指令要写
Read 读取操作数（源操作数就绪时） 源操作数未就绪（RAW stall）
Execute 执行运算（可能多个周期） 等待功能单元完成
Write 写回结果，检查WAR 目的寄存器被后续指令读（WAR stall）

⭐ 重点：

  • ✅ 允许乱序执行（Read阶段就绪即可执行）
  • ❌ 顺序写回（Write阶段检测WAR）
  • ❌ 结构冒险（WAW）在Issue阶段就stall
  • 没有寄存器重命名 → WAR/WAW相关只能靠stall

5.4.4 记分牌特点

优点：

  • 允许乱序执行，提高吞吐率
  • 集中控制，逻辑清晰

缺点：

  • 没有定向技术（forwarding）
  • 指令窗口较小，仅限于基本块内调度
  • WAR/WAW通过等待解决，效率低
  • 没有寄存器重命名

记分牌要解决什么问题

传统的 DLX 流水线是顺序发射、顺序执行、顺序完成，指令一旦遇到数据相关就只能整体 stall。记分牌的核心思想是 32：

  • 允许乱序执行（out-of-order execution）和乱序完成（out-of-order completion）；
  • 把原来的 ID 段拆成两段：
    • Issue：译码，检测结构相关；
    • Read operands：等到没有数据相关时才读操作数；
  • 用一个集中的”记分牌”硬件做相关检查与互锁。

它起源于 1963 年的 CDC 6600（4 个 FPU + 2 个访存部件 + 4 个整数部件），特点是顺序发射、乱序执行、乱序完成，并且 CDC 6600 没有采用定向（forwarding）技术，只实现了非精确中断 32。

由于引入了乱序完成，会带来 WAR 和 WAW 两类新的相关 33，记分牌必须处理它们。

四个流水段（替代原来的 ID / EX / WB）

记分牌用四段代替原来的 ID、EX、WB 三段 333536：

1. Issue（发射）—— 解决结构相关和 WAW

  • 条件：所需功能部件空闲（无结构相关），且没有其他活动指令使用相同的目的寄存器（无 WAW）。
  • 如果有结构相关或 WAW，则该指令暂停发射，且后继指令也不发射（顺序发射），直到相关解除。

2. Read operands（读操作数）—— 解决 RAW

  • 条件：先前已发射、正在运行的指令不再对当前指令的源寄存器进行写操作（或写操作已完成），则操作数有效。
  • 这一步动态地解决 RAW，因此指令可能乱序执行。

3. Execution（执行）

  • 拿到两个操作数后，功能部件开始执行；算出结果后通知记分牌”执行完毕”。

4. Write result（写结果）—— 解决 WAR

  • 检测是否存在 WAR：若有先发射的指令还没读到本指令的目的寄存器，则暂停写结果。

  • 教材里的经典例子 36：

    CDC 6600 的记分牌会暂停 SUBD 进入 Write result，直到 ADDD 读完 F8 为止。

一句话总结每种相关在哪个阶段被处理 3536：

相关 解决阶段 解决方式
结构相关 Issue 功能部件忙则不发射
WAW Issue 有同目的寄存器的活动指令则不发射
RAW Read operands 等源寄存器无人再写
WAR Write result 等先发射的指令读完该寄存器

记分牌维护三张状态表：

1. Instruction status（指令状态表）

记录每条正在执行的指令处于四个阶段中的哪一步（Issue / Read operands / Execution complete / Write result）。

2. Functional unit status（功能部件状态表）

每个功能部件用 9 个域 描述：

域 含义
Busy 该部件是否忙碌
Op 该部件执行的操作
Fi 目的寄存器
Fj, Fk 两个源寄存器
Qj, Qk 产生源 Fj/Fk 的功能部件（谁会写这两个源）
Rj, Rk 源 Fj/Fk 是否就绪

3. Register result status（寄存器结果状态表）

对每个寄存器，指出当前哪个功能部件将要写它；若没有指令要写它，则为 Blank。这张表是实现”唤醒”的关键——某条指令写完结果后，凡 Qj/Qk 指向它的部件，对应的 Rj/Rk 就被置为 Yes。

Issue

  • 等待条件：Not busy(FU) 且 not result(D) —— 功能部件空闲，且目的寄存器 D 当前没有人要写（无 WAW）。
  • 簿记： 这里 Result(S1) 就是查寄存器结果状态表：若 S1 当前正被某部件写，则 Qj 记下那个部件、Rj=No（要等）；否则 Qj=blank、Rj=Yes。

Read operands

  • 等待条件：Rj and Rk（两个源都就绪）。
  • 簿记：Rj ← No; Rk ← No（读走后标志清零，进入执行）。

Execution complete

  • 功能部件算完后通知记分牌（无特殊等待条件）。

Write result

  • 等待条件：对所有其他活动指令 f，要求 即：任何一条还没读操作数（Rj/Rk 仍为 Yes 表示还没读走）的指令 f，如果它的某个源正好等于本指令的目的寄存器，就不能写——这就是 WAR 检测。
  • 簿记： 写完后，把所有等待本结果的部件的 Rj/Rk 置 Yes（唤醒），并清除寄存器结果状态表中的登记。

这张表的精髓在于：Result 表实现”谁来写我”（RAW 跟踪），Write result 阶段的扫描实现”我写之前别人读完没”（WAR 跟踪），Issue 时的 not result(D) 实现 WAW 跟踪。

5.5 硬件方法(二)：Tomasulo算法

5.5.1 核心思想

IBM 360/91 (1971)：CDC 6600推出三年后

三大创新：

  1. Reservation Station (RS)：每个功能单元有多个RS缓冲
  2. CDB (Common Data Bus)：公共数据总线，广播结果
  3. 寄存器重命名：通过RS分配实现（消除WAR/WAW）

5.5.2 关键结构

结构 功能 字段
Reservation Station 缓存等待执行的指令和操作数来源 Op/Vj/Vk/Qj/Qk/Busy
CDB 广播执行结果，所有RS和寄存器同时监听 64位数据 + 4位源地址
Load/Store Buffer 管理Load/Store的地址计算和执行 类似RS结构
寄存器结果状态表 记录每个寄存器的值来源（RS或就绪） Qi字段

5.5.3 Tomasulo执行流程

阶段 操作 关键点
Issue (发射) 从指令队列取指令；有空闲RS则发射，标记操作数来源（RS或寄存器值） 寄存器重命名在此完成
Execute (执行) 两个源操作数都就绪时开始执行；Load还需等待地址计算完成 通过推迟执行避免RAW
Write Result (写结果) 结果通过CDB广播；所有等待该结果的RS和寄存器同时更新 广播机制，一次更新多个等待者

5.5.4 Tomasulo解决数据冒险

冒险类型 解决方式 对比Scoreboard
RAW 等待源操作数就绪（CDB广播） 相同
WAR ✅ 寄存器重命名（RS分配）→自动消除 ❌ Stall等待
WAW ✅ 寄存器重命名（RS分配）→自动消除 ❌ Issue阶段停止发射

5.5.5 Scoreboard vs Tomasulo对比

Scoreboard Tomasulo
寄存器重命名 ❌ 无 ✅ 有（通过RS）
WAR/WAW处理 Stall 自动消除
乱序写回 ❌ 顺序写回 ✅ 乱序写回
结构冲突 Issue阶段检测 RS有空即可发射
硬件复杂度 较低 较高（CDB、RS）
控制方式 集中式记分牌 分布式RS控制

关键观察：

性能提升原因：

  • CDB广播减少等待时间
  • 功能部件流水化，减少结构冲突

一、Tomasulo 算法的背景与目标 7374

  • 1966 年首次用于 IBM 360/91（比 CDC 6600 的记分牌晚三年）。
  • 目标：在没有专用编译器的情况下提高性能。
  • 为什么要另起炉灶？因为 IBM 360 的 ISA 比 CDC 6600 “抠门”：只有 4 个 FP 寄存器（CDC 6600 有 8 个）、只有 2 位寄存器描述符（3 位）、还有 memory-register 型操作。寄存器少、约束多，更需要硬件动态调度。

采用该技术的现代处理器：Alpha 21264、HP 8000、MIPS 10000、Pentium II、PowerPC 604……

二、和记分牌的三大本质区别

这是理解 Tomasulo 的钥匙：

维度 记分牌（Scoreboard） Tomasulo
控制与缓存 集中在记分牌 分布在各功能部件的”保留站 (Reservation Station, RS)”
操作数来源 从寄存器读 从 RS 读，结果走 公共数据总线 CDB 广播
寄存器名 保留原名 寄存器重命名 (Register Renaming)：指令中的寄存器被替换成”值”或”指向 RS 的指针”
WAR / WAW 靠停发射/停写来回避 靠重命名从根本消除
定向技术 不采用 通过 CDB 广播实现等价的”定向”

关键点：RS 的数量多于寄存器，因此可以做编译器做不到的重命名优化。Load/Store 部件也被当成带 RS 的功能部件处理；而且 Tomasulo 允许操作队列跨越分支（不局限于基本块）。

三、硬件组织

核心是一条 Common Data Bus (CDB)：

  • 普通总线是 data + destination（”去哪儿”总线）；
  • CDB 是 data + source（”从哪儿来”总线）：64 位数据 + 4 位功能部件源地址，采用广播方式。
  • 任何 RS 只要自己的 Qj/Qk 等于 CDB 上的 source 标签，就”接住”这个结果——这就是”定向/唤醒”机制 78。

四、保留站（RS）的结构

每个 RS 有这些域：

域 含义
Op 该部件执行的操作
Vj, Vk 两个源操作数的值（Store 缓冲区的 Vk 存要写入内存的值）
Qj, Qk 产生源操作数的 RS 编号（=0 表示就绪，替代了记分牌里的 Rj/Rk 标志）
A 存储器地址：先存立即数偏移，算出有效地址后存有效地址
Busy RS/FU 是否占用

另有 Register result status 表（寄存器结果状态表）：对每个寄存器记录哪个 RS 将要写它，记作 Qi。这与记分牌的 Register result status 类似，只是 Qi 指向 RS 而非 FU。

五、三阶段控制逻辑

阶段 1：Issue（发射）—— 消除 WAR、WAW

等待条件：有空闲 RS（无结构相关）。

簿记（以 FP 操作为例，rs/rt 源、rd 目的）：

Load/Store 的发射类似，但要把立即数放进 A，且 Store 只登记要写内存的数据来源（RegisterStat[rt]）。Load 会在 RegisterStat 中登记 Qi（因为要写寄存器），Store 不会。

这里就是”重命名”的本质：指令不再用寄存器名 rs/rd 互相引用，而是改成用 RS 编号 r 来标记”谁产生这个值”。后续写同一个 rd 的指令拿到的是新的 r，于是 WAR/WAW 被自然消除——因为它们引用的是不同的 RS，不是同一个寄存器名。

阶段 2：Execution（执行）—— 回避 RAW

FP 操作：

  • 等待条件：Qj = 0 and Qk = 0（两源都已就绪）；
  • 否则监听 CDB，等到对应的源标签出现就把值填进 Vj/Vk 并清 Qj/Qk；
  • 两源就绪后执行，结果存在 RS 里。

Load/Store 分两步 80：

  • Step1：等 Qj=0（基址寄存器就绪）且自己是 load/store 队列队首 → 计算 A ← Vj + A（有效地址）；
  • Load Step2：等 Step1 完成 → 读 Mem[A]；
  • Store 则等数据就绪后在 Write 阶段写入内存。

阶段 3：Write result（写结果）—— 广播

FP 操作 / Load：

  • 等待条件：执行完成 且 CDB 空闲；
  • 簿记（广播给所有等待者）： 这段就是”一次广播，同时唤醒所有等待者”。

Store：

  • 等待条件：执行完成 且 RS[r].Qk = 0（要写入的数据已就绪）；
  • 簿记：Mem[RS[r].A] ← RS[r].Vk; RS[r].Busy ← no。

七、与记分牌的对比（第 103 页）103

  1. 结构冲突：Tomasulo 有多个 RS/Load Buffer，不会因为部件被占而停发射；
  2. WAR、WAW 冲突：重命名直接消除，不再需要停发射/停写；
  3. 没有定向技术：记分牌不定向，而 Tomasulo 靠 CDB 广播实现转发。

八、Tomasulo 的局限与伏笔

  • CDB 是单点瓶颈：只有一条 CDB，多个部件同时完成时要竞争；
  • Tomasulo 本身处理不了控制相关——它”可以跨越分支”只是把指令取进 FP 操作队列，并没有真正的推测执行。把分支预测、重排序缓冲（ROB）加上去，就演变成现代处理器的推测执行 + 乱序执行核心；
  • 后来 寄存器重命名 + ROB 成了主流（如 Pentium Pro 以后），而 Tomasulo 的 RS+CDB 思想被保留为”唤醒/转发”机制的基础。

5.6 硬件推测执行

5.6.1 为什么需要推测执行？

问题：

  • 控制相关（分支）限制了跨基本块的并行性
  • 分支前不知道方向→不敢执行分支后的指令

解决：推测：猜测分支方向，先执行，猜错则回滚

5.6.2 Reorder Buffer (ROB)

核心结构：推测执行结果的缓冲区

ROB + Tomasulo = 完整的推测执行机制

工作原理：

  1. 指令执行完成后先写入ROB，而非直接写寄存器
  2. 分支确认正确后，ROB中的结果**按序提交(Commit)**到寄存器
  3. 分支猜错→flushROB中该分支之后的所有条目

5.6.3 ROB + Tomasulo执行流程

阶段 操作 新增功能
Issue 发射到RS，同时分配ROB条目 ROB编号用于跟踪
Execute 同Tomasulo 无变化
Write Result 结果写入ROB（而非寄存器） 等待提交
Commit ROB头部指令确认无误，结果写入寄存器；若是分支则确认/取消推测 新增阶段，保证精确中断

⭐ 重点：

  • In-order issue/commit, out-of-order execution/writeback
  • ROB提供精确中断支持
  • 分支预测失败时，flush ROB恢复状态

5.6.4 精确中断 (Precise Exceptions)

问题：乱序完成加大了实现精确中断的难度

解决：顺序提交（Commit）

  • 提交指令的完成顺序必须与指令发射顺序相同
  • 精确中断的返回地址之前的所有指令都已完成
  • 其后的指令都还没有完成

5.6.5 完整示例对比

代码序列：

性能对比（假设执行时间：LD=1, MULT=10, SUBD/ADDD=2, DIVD=40）：

指令 Scoreboard Tomasulo Tomasulo+ROB
LD F6 4 4 4 (commit)
LD F2 8 5 5 (commit)
MULT F0 20 16 16 (commit)
SUBD F8 12 8 17 (commit)
DIVD F10 62 57 57 (commit)
ADDD F6 22 11 58 (commit)
Total 62 57 58

观察：

  • ROB增加了commit阶段的延迟
  • 但提供了精确中断和推测执行能力
  • DIVD指令执行时间最长（40 cycles），限制了整体性能

5.7 分支预测技术

5.7.1 分支预测的重要性

性能公式：

$$
Performance = f(accuracy, cost\ of\ misprediction)
$$

预测错误代价：Flush Reorder Buffer

5.7.2 静态分支预测

方法：

  • 编译时预测
  • 常用策略：总是预测不跳转、总是预测跳转、根据操作码预测

缺点：无法适应运行时行为

5.7.3 动态分支预测：BHT (Branch History Table)

1-bit BHT

结构：

  • 分支指令的PC低位索引
  • 记录上一次转移是否成功（1位）
  • 不做地址检查

问题：循环中2次预测错误

  • 最后一次循环：前面预测成功，实际需要退出
  • 首次循环：前面预测失败，实际成功

2-bit BHT

状态机：

优势：

  • 需要2次连续错误才改变预测
  • 循环中只有1次预测错误（退出时）

BHT准确率

影响因素：

  • 表大小：4096项的表错误率1%-18%
  • 预测器类型：Basic 2-bit, Correlating, Local, Tournament

典型准确率：

  • Basic 2-bit BHT (4096 entries): 82%-99%
  • Correlating predictor (2,2): 85%-99.5%

5.7.4 关联预测器 (Correlating Predictor)

思想：根据其他分支的行为预测当前分支

示例：

观察：第3个分支与前2个分支相关

表示方法：(m, n)预测器

  • 根据最近m次分支，从2^m个预测器中选择
  • 每个预测器n位

示例：(2, 2)预测器 = 2位全局历史 + 2位局部预测

5.7.5 竞赛预测器 (Tournament Predictor)

结构：

  • 局部预测器：根据该分支的历史预测
  • 全局预测器：根据所有分支的历史预测
  • 选择器：动态选择哪个预测器更准确

Alpha 21264竞赛预测器：

  • 局部预测器：1024表项 × 10位历史 → 1024个2位预测器
  • 全局预测器：4096表项（2^12全局历史）
  • 选择器：4096表项（2位计数器）

5.7.6 分支目标缓冲区 (Branch Target Buffer)

目的：预测分支目标地址

结构：

  • 分支指令地址 → 预测的目标地址
  • 包含预测状态位

工作流程：

  1. 取指时查找BTB
  2. 如果命中且预测taken，使用预测地址
  3. 如果预测错误，flush流水线

5.7.7 分支预测性能

总分支代价计算：

$$
Total\ penalty = Misprediction\ rate \times Branch\ frequency \times Misprediction\ penalty
$$

示例假设：

  • 预测准确率：90%
  • 命中率：90%
  • 分支频率：20%
  • 预测错误代价：10 cycles

$$
Effective\ CPI = Base\ CPI + 0.20 \times (1-0.90) \times 10 = Base\ CPI + 0.2
$$

5.8 多发射处理器

5.8.1 如何使CPI < 1？

两种基本方法：

Superscalar VLIW
每周期指令数 不定（1-8条） 固定（4-16条）
调度者 硬件（运行时） 编译器（编译时）
硬件复杂度 高 低
编译器复杂度 低 高
二进制兼容 ✅ 好 ❌ 差
代表 Intel Core, AMD Zen, ARM Cortex IA-64 (Itanium), DSP

5.8.2 超标量 (Superscalar)

定义：硬件在运行时动态发现并调度可并行执行的指令

要求：

  • 译码和发射多条指令
  • 检查多条指令之间的相关
  • 动态调度

示例：双发射超标量

  • 每周期发射1条FP + 1条Integer指令
  • 理想CPI = 0.5（假设50% FP操作，无相关）

实际性能：由于相关和资源限制，难以达到理想CPI

5.8.3 VLIW (Very Long Instruction Word)

定义：编译器将多条不相关的操作打包到一条超长指令中

特点：

  • 所有操作由编译器组合，相互无关
  • 指令字较长（112-168位）
  • 需要编译器解决分支问题

EPIC (Explicitly Parallel Instruction Computing)：

  • IA-64 (Itanium)采用
  • 显式并行指令计算

优势：

  • 硬件简单（无需动态调度）
  • 可使用多个寄存器文件而非多端口寄存器文件

劣势：

  • 完全依赖编译器
  • 二进制兼容性差
  • 代码膨胀（循环展开 + VLIW中无用字段）

5.8.4 Trace Scheduling

目的：消除分支，提高VLIW效率

两步：

  1. Trace Selection：搜索最长的直线型代码（trace）
  2. Trace Compaction：将trace中的指令拼装为若干条VLIW指令

恢复机制：编译器插入保存环境的代码，处理预测错误

5.8.5 多发射处理器性能示例

循环展开对比：

方法 每次迭代cycles 相对原始版本
原始循环 10 1.0×
循环展开 + 调度 3.5 2.9×
Superscalar (2-way) 2.4 4.2×
VLIW (展开7次) 1.3 7.7×

⭐ 结论：多发射技术可显著提高性能，但受限于程序内在并行性

5.9 多线程技术

5.9.1 背景

问题：从单线程程序挖掘ILP越来越困难

解决：利用线程级并行（TLP）提高处理器利用率

5.9.2 多线程分类

类型 粒度 切换时机 优点 缺点
Fine-grained 指令级 每个周期切换 消除垂直浪费 仍存在水平浪费
Coarse-grained 线程级 长延迟操作（Cache miss） 切换开销小 仍存在垂直浪费
SMT 指令级 动态调度选择 同时利用ILP和TLP 硬件复杂

5.9.3 细粒度多线程 (Fine-grained MT)

特点：

  • 多个线程的指令交叉执行
  • 每个周期切换线程

示例：CDC 6600 Peripheral Processors

  • 10个I/O线程交替执行
  • 每1000ns执行一条指令/线程

5.9.4 粗粒度多线程 (Coarse-grained MT)

切换时机：

  • Cache失效
  • 等待同步结束

示例：

  • IBM PowerPC RS64-IV：L2 cache miss时切换线程
  • MIT Alewife：local cache miss时切换

5.9.5 同时多线程 (SMT)

定义：在相同时钟周期运行多个线程的指令

特点：

  • 使用OoO superscalar的指令窗口
  • 从多个线程选择指令发射
  • 任何单线程可使用整个系统资源

代表：

  • Intel Pentium 4 (Hyperthreading)：2-way SMT
  • IBM Power 5：2-way SMT
  • Intel Nehalem/Core i7：2-way SMT

SMT性能：

  • Pentium 4 SPECint_rate: 1.01×, SPECfp_rate: 1.07×
  • Power 5 SPECint_rate: 1.23×, SPECfp_rate: 1.16×

5.9.6 多线程效率对比

Superscalar效率问题：

  • 垂直浪费 (Vertical waste): 完全空闲的发射周期
  • 水平浪费 (Horizontal waste): 部分填充的发射周期 (IPC < Issue width)

解决方法：

  • Fine-grained MT: 减少垂直浪费
  • Coarse-grained MT: 减少垂直和水平浪费
  • SMT: 同时减少垂直和水平浪费
  • CMP: 在核间静态分配发射宽度

5.10 ILP的限制

5.10.1 理论上限：理想机器

实验条件：

  • 无限指令窗口
  • 完美的分支预测
  • 完美的寄存器重命名
  • 完美的别名消除

结果（IPC）：

  • 整数程序：18 - 60 IPC
  • 浮点程序：75 - 150 IPC

⭐ 结论：理论ILP很大，但实际硬件难以达到

5.10.2 现实限制

1. 分支预测影响

条件：2000指令窗口，64发射，2-bit BHT

结果（IPC）：

  • 整数程序：6 - 12 IPC
  • 浮点程序：15 - 45 IPC

性能下降：理想情况的20%-30%

2. 寄存器重命名限制

条件：256个重命名寄存器

结果（IPC）：

  • 整数程序：5 - 15 IPC
  • 浮点程序：11 - 45 IPC

3. 内存别名限制

条件：完美的别名消除

结果（IPC）：

  • 整数程序：4 - 9 IPC
  • 浮点程序：4 - 45 IPC（Fortran无堆）

4. 窗口大小限制

条件：窗口从∞减少到16

结果（IPC）：

  • 整数程序：4 - 7 IPC
  • 浮点程序：8 - 45 IPC

5.10.3 现实处理器性能

典型配置（2000年代）：

  • 指令窗口：16 - 256条指令
  • 发射宽度：2 - 8条指令/周期
  • 分支预测：8K - 16K 2-level预测器
  • 重命名寄存器：32 - 256个

实际IPC：

  • 整数程序：2 - 4 IPC
  • 浮点程序：4 - 8 IPC

⭐ 结论：现实处理器只能挖掘理论ILP的一小部分

5.11 存储器消歧 (Memory Disambiguation)

5.11.1 问题

示例：

问题：这两个操作是否相关？即 0(R2) == 0(R3)?

5.11.2 处理方法

非投机方式

原则：当前存储器指令之前的store指令计算存储器地址后，才能执行当前的存储器操作

方法：

  • Total Ordering: 完全按序执行
  • Partial Ordering: Load前的store完成地址计算后才执行Load

投机方式

原则：假设Load与之前的store无关，先执行，错误时回滚

硬件支持：

  • Load Queue: 存储load操作的物理地址
  • Store Queue: 存储store操作的物理地址和数据
  • Wait Table: 记录load超越store的情况

5.11.3 MIPS R10000方法

结构：

  • Load/Store Queue: 16项队列
  • Indetermination Matrix: 16×16矩阵，记录地址计算状态
  • Dependency Matrix: 16×16矩阵，记录load对store的依赖

工作流程：

  1. load/store指令进入队列时，设置对应位
  2. 计算有效地址时，清除对应位
  3. load操作对应的行全0时，方可执行

  • 分支预测
  • 多发射（Superscalar、VLIW）
  • 多线程（Fine-grained、Coarse-grained、SMT）

关键思想

寄存器重命名：消除名字相关（WAR/WAW），是现代处理器的核心

动态调度：硬件在运行时发现并行性，不依赖编译器

推测执行：猜测分支方向，提高跨基本块的并行性

多发射：突破CPI=1的限制，通过ILP和TLP提高性能

性能限制

理论限制：程序本身的并行性

现实限制：

  • 分支预测准确率
  • 寄存器数量
  • 指令窗口大小
  • 内存别名
  • 硬件复杂度

实际性能：只能达到理论ILP的10%-30%
